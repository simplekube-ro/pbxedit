# Design

## Context

The repository holds only `docs/design.md` and OpenSpec scaffolding. This change creates the package and its bottom layer. See proposal.md for motivation and `docs/design.md` § Architecture 1 for the layer's place.

Constraints that shape the approach:

- Real project files reach 10,000+ lines and mix formatting styles; the originating project has two indentation depths for `PBXGroup` blocks and 420 non-hex object IDs.
- Callers in the next layer address content structurally (`objects` → ID → key), so they need stable addressing across edits.

## Goals / Non-Goals

**Goals**

- `serialize(parse(x)) == x` as a property that tests can assert over any corpus.
- Edits whose diff is predictable from the edit alone.
- An API small enough that `PBXModel` is the only consumer that needs to understand trivia.

**Non-Goals**

- Incremental reparsing, or performance work beyond "a 10,000-line file parses in well under 100 ms".
- A general property-list library. Only what `project.pbxproj` uses is supported.

## Decisions

### D1. Value-type tree with trivia owned by tokens

Every token owns its **leading** trivia (whitespace and comments before it). A final end-of-file token owns whatever follows the last real token. Nodes are value types:

- `Dictionary`: ordered array of entries `(key token, "=" token, value node, ";" token)`.
- `Array`: ordered array of elements `(value node, optional "," token)`.
- `String`: one token holding the **raw** text, quotes and escapes included; the decoded value is computed on demand.
- `Data`: one opaque token.

Serialization is the concatenation of every token's trivia and text in order. Round-trip fidelity is then true by construction, not by care.

*Alternative considered:* a red/green tree with parent pointers, as in SwiftSyntax. Rejected — it buys incremental reparsing and identity-stable nodes, neither of which is needed for a file rewritten once per invocation.

*Alternative considered:* a flat token list with ranges. Rejected — inserts shift every later range.

### D2. Comments after a value belong to the next token

In `A1 /* Foo.swift */,` the comment is leading trivia of `,`. In `A1 /* name */ = {` it is leading trivia of `=`. This keeps one rule (leading only) and means removing an element removes its annotation comment with it, because element removal takes the value token through the separator token inclusive.

### D3. Structural paths, not node references

Callers address nodes by path: a sequence of dictionary keys and array indices from the root. Paths stay valid across unrelated edits because dictionaries are keyed. The next layer mostly uses `["objects", <ID>, <key>]`.

### D4. Parse bytes, not characters

The lexer runs over `UInt8`. All structural characters are ASCII, so multi-byte UTF-8 passes through untouched inside strings and comments, and offsets are exact. UTF-8 validity is checked once, up front, to give the byte-offset error the spec requires.

### D5. Accept what Apple's reader accepts; write what Xcode writes

The bare-string character set accepted on **read** is CoreFoundation's old-style set: letters, digits, `_ $ / : . -`. The set left bare on **write** is Xcode's narrower one: letters, digits, `_ $ / .`, and not containing `//` or `___`. Files produced by other tools often have bare hyphens; rejecting them would make the tool unusable on exactly the projects that need it, and rewriting them would violate "touch nothing else".

This refines `docs/design.md` rule S5 ("quoted if and only if it requires quoting"): a bare string with an illegal character is already a parse error, so what remains of S5 is a style finding on non-canonical quoting. `integrity-rules-lint` records that in `docs/design.md`.

### D6. Formatting by sibling

For an insertion the layer picks a **template sibling**: the element before the insertion point, else the one after. It copies that sibling's leading whitespace (from the last newline onward), and whether its separator is followed by a newline. For an empty container it uses the closing delimiter's indentation plus one tab. Comments are never copied; callers pass the annotation comment for the new node explicitly.

### D7. Errors are values

`parse` returns a result carrying `ParseError(line, column, byteOffset, expected, found)`. No `fatalError`, no force unwraps, no recursion without a depth limit (nesting deeper than 64 is a located error).

## Risks / Trade-offs

- [The accepted grammar diverges from Xcode's in some corner] → The corpus test is the guard. Task 7 builds the corpus from projects generated by current and older Xcode versions plus the originating project; any file Xcode opens that fails to parse is a bug.
- [Corpus files carry third-party licences] → Generate fixtures with Xcode's templates and hand-derive variants; include third-party files only under MIT/Apache with attribution in `Tests/Fixtures/NOTICE`.
- [Value-type tree copies on every edit] → Arrays of entries are copy-on-write; an edit copies one container's entry array. Measured in task 8; acceptable unless a 10,000-line file takes over 100 ms for parse + 100 edits + serialize.
- [Sibling formatting picks a misleading template] → Containers in project files are homogeneous in practice; the spec scenarios pin the three shapes that occur (multi-line array, single-line dictionary entries, empty array).

## Open Questions

- Whether Xcode 27 changed the canonical quoting rule relative to earlier versions. Resolved by inspecting corpus output in task 7; affects only the write-side character set in D5, not the API.
